## Live deployment verification (192.168.1.195, 2026-08-23)

Deployed via `scripts/deploy.ps1`'s approach (run manually step-by-step during first deploy, since three real deployability bugs surfaced that the script itself needed fixing for — all fixed and folded back into `deploy.ps1`, `Dockerfile`, `docker-compose.yml`, `env.ts`, `prisma/schema.prisma` and the migration files before this was recorded as done):

**Bugs found only by actually deploying (docs-pack/docs/25's whole point — "a mock is not proof"):**
1. Docker build context couldn't reach `docs-pack/` (a sibling of `hunt-app/`) — Dockerfile/compose context widened to the repo root.
2. `GRAPH_REDIRECT_URI=` (blank from compose's `${VAR:-}` interpolation) crashed `env.ts`'s zod validation, which treated a defined empty string differently from an absent one — fixed to treat blank as absent.
3. Prisma's query engine failed to load on `node:20-alpine` (`libssl.so.1.1: No such file or directory`) — the base image ships no OpenSSL at all, so Prisma's own version-probe defaulted to a guess that doesn't match Alpine 3.19+'s OpenSSL 3.x. Fixed with explicit `binaryTargets` in `schema.prisma` plus `apk add openssl` in both Dockerfile stages.
4. Both `migration_lock.toml` and the initial migration's `migration.sql` had a UTF-8 BOM (from PowerShell's `Out-File -Encoding utf8` when they were first generated in Sprint 1) that Postgres's SQL parser rejected outright (`syntax error at or near "﻿"`) — neither file had ever actually been run through `prisma migrate deploy` until this point. Both re-written without a BOM.
5. `prisma` was a devDependency; the production image's `npm ci --omit=dev` would have stripped it, breaking `src/db/migrate.ts`'s runtime `npx prisma migrate deploy` call — moved to a regular dependency (fixed in Sprint 7 part 1, before the deploy attempt, but confirmed necessary here).

**What was proven live**, via `docker compose up -d --build`, `prisma migrate deploy`, `node dist/db/seed.js`, and real HTTP calls against `http://192.168.1.195:3020`:
- `GET /health` → `200 {"status":"ok"}`
- `docker ps` shows `hunt-app: healthy`, `hunt-postgres: healthy`, `hunt-redis: healthy`, `restart: unless-stopped` on all three
- Both migrations applied cleanly to a real Postgres 16 database
- Seed succeeded (confirms the `Company.name @unique` fix from Sprint 1 works — the original scaffold's seed would have failed here)
- `POST /hunt/run` against the **live** Jobicy API and JobsCollider RSS feed: `{"coveragePercent":100,"sourcesSucceeded":["jobicy","jobscollider"],"sourcesFailed":[],"totalOpportunitiesFound":20,"totalOpportunitiesNew":20}`
- Of those 20 real opportunities: 10 correctly `INELIGIBLE`/`EXCLUDED` (permanent roles, per the seeded contract-type preferences) with `fitScore: null`; 10 correctly `ELIGIBLE` with a computed `fitScore` and `actionability: REVIEW` (gaps present — contract type not confirmed by the source)
- `GET /audit` shows a real `hunt.run` AuditEvent with the run's full metadata
- `GET /companies` returns the 4 seeded companies
- `GET /commercial/benchmark` correctly returns `sufficientData: false` rather than fabricating a benchmark from the (zero, in this run) rate-bearing opportunities

**Still NOT VERIFIED IN THIS ENVIRONMENT**: any AI-dependent path (BIDOPS, reply classification — no freellmapi key), any real Graph send/reply ingestion (no Entra app registered), and a physical host-restart survival test (not performed — this is a shared host also running AEOS, freellmapi and other production workloads; `restart: unless-stopped` is set and confirmed on all three containers as the structural guarantee instead).
