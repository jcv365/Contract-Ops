# HUNT Phase 1 — Claude Code Governing Instructions

## Mission

Build Phase 1 of a personal AI Contract Acquisition OS for one primary user.

The immediate objective is not to build a generic SaaS product. The objective is to start finding and pursuing real worldwide remote contract opportunities for the user as quickly as possible.

Phase 1 must support two acquisition engines:

1. **Opportunity Hunt** — find live, relevant, remote-compatible contract opportunities worldwide.
2. **Market Outreach Hunt** — find verified recruiters and professional/consulting companies worldwide that should receive the user's CV and/or company capability profile.

The system must support:
HUNT → validation → scoring → BIDOPS positioning → human approval → Microsoft Graph/Outlook sending → reply intelligence → opportunity creation.

## Non-negotiable rules

1. Read all files in `docs/`, `prompts/`, and `adr/` before implementing architecture changes.
2. Inspect the existing repository before adding dependencies or rewriting functionality.
3. If this project is based on Career-Ops, preserve useful existing functionality and reuse it where practical. Do not rewrite working subsystems without evidence.
4. Inspect existing AEOS/BIDOPS/HUNT components if present. Reuse existing contracts, adapters, evidence layers, model routing and infrastructure where appropriate.
5. Do not send email autonomously. AI may research, draft, score, validate and recommend. A human must explicitly approve every outbound email.
6. Never guess or infer an email address.
7. A recruiter may only be addressed by name when a named email address has been independently verified. If only a verified generic/team email exists, address the company/team.
8. Never fabricate recruiter identities, client names, rates, availability, certifications, projects, experience, company resources or opportunity details.
9. Every candidate/company claim generated by BIDOPS must have evidence.
10. Never treat an advert saying "remote" as proof of remote eligibility. Validate geography, onsite requirements, clearance, language, work authorisation and contract status.
11. Foreign rates must retain original currency/rate and also have a ZAR equivalent with timestamped FX source/rate.
12. Do not report worldwide coverage unless the configured worldwide source/country coverage matrix was actually searched. Report coverage and gaps.
13. Hard-filter failures must not receive a high actionable fit score. They may be recorded as excluded with a clear reason.
14. Respect source terms, API terms, licensing, rate limits, robots directives where applicable, attribution requirements and anti-bot controls. Do not bypass access controls.
15. Store source provenance for every opportunity and recruiter record.
16. Protect OAuth tokens, personal data, CVs and email content. Never log access tokens or secrets.
17. Use least-privilege Microsoft Graph permissions.
18. Build API-first boundaries so later SaaS/multi-tenant expansion does not require a rewrite, but do not implement SaaS billing or marketplace features in Phase 1.
19. Use small, reviewable implementation sprints. Run tests after changes.
20. If a requirement conflicts with repository reality or another authoritative document, stop and document the conflict rather than silently choosing.

## Phase 1 definition of done

The system must be capable of:

- running a worldwide opportunity search;
- searching and recording source coverage;
- normalising and deduplicating opportunities;
- validating remote/contract/eligibility constraints;
- scoring opportunities against the approved profile;
- converting foreign rates to ZAR;
- discovering recruiters;
- discovering professional/consulting companies and relevant buyer contacts;
- verifying usable recruiter/company email addresses;
- distinguishing named verified emails from generic/team emails;
- generating evidence-backed BIDOPS outreach;
- selecting CV vs company profile vs both;
- requiring human approval;
- sending approved messages through Microsoft Graph/Outlook;
- recording send/audit state;
- ingesting approved mailbox replies if Mail.Read is enabled;
- classifying replies and extracting potential opportunities;
- showing the user a clear pipeline and next actions.
